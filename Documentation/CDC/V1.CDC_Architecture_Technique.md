## Interconnexion des modules — Bus d'événements interne

Puisque c'est **un seul plugin modulaire**, les modules ne communiquent pas via une API externe mais en interne. Approche recommandée : **bus d'événements interne**, sur le modèle des events Bukkit natifs.

```
Exemple :
  EcoModule déclenche un événement interne "PurchaseCompletedEvent"
  ReputationModule écoute cet événement et ajuste la réputation
  -> EcoModule n'a pas besoin de connaître ReputationModule directement

Avantages :
  - Modules faiblement couplés — plus faciles à maintenir/tester séparément
  - Ajouter un nouveau module qui réagit à un événement existant
    ne nécessite pas de modifier le module émetteur
```

> À confirmer avec l'équipe de dev une fois assignée — alternative possible : appels directs entre modules si le bus d'événements est jugé trop complexe pour la taille de l'équipe.

## Convention MySQL — Principes de base

- Une table par module principal (`wayrift_factions`, `wayrift_reputation`, `wayrift_claims`, etc.)
- UUID joueur comme clé de référence standard (pas pseudo, qui peut changer)
- Horodatage (`created_at`, `updated_at`) sur les tables à historique (logs, transactions, variations de réputation)

> Schéma détaillé table par table — à faire une fois le développement lancé, pas nécessaire au stade actuel de conception.
